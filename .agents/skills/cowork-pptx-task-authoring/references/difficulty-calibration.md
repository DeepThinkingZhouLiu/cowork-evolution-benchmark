# PPTX 难度设计与实测校准

## 两层标签

- `design_target`：制题阶段的候选层级，只用于控制题池结构，写入适配记录和建设台账。
- `difficulty_level` / `difficulty_tier`：冻结协议下的实测层级。真实回放前必须同时为 `unassigned`。

Rubric/Judge 只判断答案质量。难度来自同一 Agent、工具、时间和资源预算下的实际成功率、得分与执行负担。

## PPT 域内设计目标

| 目标 | 典型结构                                                                 |
|------|--------------------------------------------------------------------------|
| L1   | 单一明确输入；局部创建或编辑；事实直接给出；约束少且无冲突；短路径可完成。 |
| L2   | 多页或多素材；需要保持未修改内容、模板或叙事一致；有一次数据转换或审计。   |
| L3   | 跨应用取证、跨文件整合、受众改写或数据分析与可视化耦合；约束相互依赖。     |
| L4   | 长时程、多阶段、动态更新、冲突来源、隐藏状态或失败恢复；强 Agent 仍易漏检。 |

页数、文件数、图片数和人工耗时只能作为描述特征，不能单独决定难度。L4 也不能靠模糊审美、故意缺文件或不合理超时制造。

## 建设配比

PPT 模块最终保留 60 题，目标为：L1 12、L2 18、L3 18、L4 12。现有题和新增题先标 `design_target`，全部通过 Harbor 与 Judge 门槛后再统一回放。

## 冻结回放协议

1. 固定三个强 Agent Harness 配置、模型版本、工具权限、上下文策略、单题 30 分钟、2 CPU、4 GiB 内存、12 GiB 存储和默认无公网。
2. 每个 Agent Harness 对每题独立运行 3 次，共 9 次；基础镜像、任务 commit 和随机种子写入清单。
3. 记录 normalized reward、严格通过、运行时间、Agent 步数、工具错误、超时和基础设施失败。基础设施失败重跑且不计入难度。
4. 用 9 次运行的平均 reward 与严格通过率为主要依据；耗时、步骤和恢复行为只用于同档排序及诊断。
5. 难度筛选所用轨迹不得再进入论文正式评测结果；final 集不得用于题目或评测配置的选择。

在题库建设期可以先做试校准：每个冻结Harness对每题保留一份有效答案，用于发现Judge地板效应、检查分档方向和审计边界题。已完成的试校准可以写回 `task.toml` 和 `metadata/task.json` 的难度字段，但必须在 `notes` 保存 `calibration_status=pilot_single_panel` 与逐题来源清单，不能宣称已完成多模型、多次重复验证。没有有效实测依据的新题仍保持 `unassigned`。2026-09-17主线已按此规则同步240题，见 `benchmarks/difficulty-labels-v0.5.csv`。

## 排序分档与冻结规则

视觉任务先计算最终混合分：

```text
combined_reward = 0.7 * deterministic_reward + 0.3 * visual_reward
```

非视觉任务的 `combined_reward` 等于 `deterministic_reward`。任一 Harness、模型、渲染器或 API 的基础设施失败都必须重跑，不得作为 0 分进入难度计算。

对任务 `i`，先计算冻结 Panel 在全部有效重复上的平均最终分 `panel_mean_i`，再令经验难度 `d_i = 1 - panel_mean_i`。PPT 模块按 `panel_mean_i` 从高到低排序，并使用建设阶段预先约定的 12 / 18 / 18 / 12 配比：

- 第 1–12 名：L1 / Easy。
- 第 13–30 名：L2 / Medium。
- 第 31–48 名：L3 / Hard。
- 第 49–60 名：L4 / Expert。

分档是 PPT 域内相对难度，不把某个绝对 reward 阈值解释成跨领域通用难度。四个领域使用同一套冻结 Panel、最终 reward 和重复运行协议，但各自在领域内排序，并保留自己的结构审计标准。

边界题必须回看 PPT 结构难度：操作范围、证据依赖、推理与综合、PowerPoint 结构深度和约束耦合。如果边界两题同分，结构更简单者进入较容易档；仍无法区分时再按稳定任务编号排序。若排序与结构预期严重冲突，先检查 Judge、环境、任务歧义和 Agent 偶然失败，不能为了维持旧标签修改分数。若某题所有 Agent 都为 0，必须先证明 Oracle、人类复核和环境稳定；不可解或主要靠猜审美的题直接淘汰，不得作为 Expert。

正式冻结时必须把所用 Harness、模型、种子、任务 commit、Judge 版本、代码分、VLM 分和最终分写入校准清单。若边界审计发现题目本身不合格，应从已审计但未冻结的 Seed 中替换，不得通过修改 Judge 或选择性删除有效运行来改变排名。
