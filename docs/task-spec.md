# 单题制作规范

## 目标

一条 CoworkEvoBench 数据是一个可独立运行、产生真实办公文件并自动评分的 Harbor 任务包，不是单独一条用户指令，也不是只有操作轨迹的数据记录。

## 必需内容

- `instruction.md`：真实用户请求、角色上下文、输入说明、输出位置和交付要求。
- `task.toml`：任务元数据、运行资源、超时、联网要求和 Judge 环境变量契约。
- `rubric.json`：不少于六条原子判据，采用统一版本 Schema。
- `environment/`：可复现运行环境，固定工具和依赖版本。
- `data/input_files/`：Agent 可见且随包交付的全部输入文件。
- `solution/`：评测侧可见的 Golden、参考脚本和必要说明。
- `tests/`：一键运行的 Judge 入口和判分实现。
- `metadata/provenance.json`：来源、许可、哈希、隐私状态和改写记录。

## 可见性

Agent 可见：

- 完整用户指令。
- 随任务提供的输入文件。
- 明确允许公开的运行环境和输出路径。

Agent 不可见：

- Golden 办公文件与参考解法。
- 完整 Rubric、Judge 提示词和隐藏断言。
- 任务属于哪个 Benchmark 分区。
- 其他 Harness 的产物与最终得分。

## 题目质量门槛

- 请求必须要求可验证的实际交付物，不能只是开放式聊天或泛泛建议。
- 输入文件必须完整、可读取、无临时链接，并记录 SHA256。
- Golden 必须能打开、可编辑，且由人工检查专业质量。
- Rubric 必须客观、原子、有区分度，并覆盖多个维度。
- Judge 必须能区分 Golden、轻微缺陷、明显错误和无效文件。
- 同一输出重复评分至少五次时，随机 Judge 的标准差应小于 `0.05`。
- 难度筛选与正式评测必须使用不同的模型运行记录，避免人工围绕单一模型过拟合题目。

## Rubric 约定

- 正向项权重大于零，分数表示满足程度。
- 惩罚项权重小于零，分数表示违规严重程度。
- 门槛项用于文件损坏、完全缺失或关键要求失败等不可被其他优点抵消的情况。
- 数据准确性、事实性和核心业务要求应获得较高权重。
- 文件命名和普通格式要求可以作为低权重项，但不能主导总分。

## 来源数据转化

真实历史轨迹只能作为候选来源。转成正式题目时至少经过：

```text
原始请求与文件
-> 隐私和许可审查
-> 交付物目标筛选
-> 输入文件恢复与哈希
-> 指令澄清但保留真实意图
-> Golden 制作
-> Rubric 与 Judge 制作
-> 正负样本校准
-> 难度 Rollout
-> 泄漏分组
-> Benchmark Release
```
