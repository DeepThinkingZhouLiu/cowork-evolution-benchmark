# Cowork-Bench 学术会议程序委员会任务逐题适配记录

## 为什么选择这道题

上游任务要求从 forms 申请和 Teamly 评审中合并 10 份记录，计算决策，安排三天会议日程，再把同一结果传播到 Excel、Word、Teamly 页面和十封邮件。它的核心不是“文件多”，而是一个错误决策或排期会同时污染四类交付物，适合补充 `shared_source_multi_output` 家族。

结构设计目标为 L3 / Hard：三份来源、30 个评分、公式化决策、带容量约束的排期、四个耦合交付物和十个隐私隔离通知共同构成深耦合。按照项目规则，正式难度仍保持 `unassigned`，直到官方 Harbor 回放和冻结多 Harness Rollout 完成。

## 实际读入上下文的上游材料

- `docs/task.md`：完整俄文 Query、三天分会场规则、录用阈值和十封通知要求。
- `docs/agent_system_prompt.md`、`task_config.json`：原工作区和 forms、Teamly、Excel、Word、email 工具约束。
- `preprocess/main.py`：10 份申请的全部字段、30 个评审分、表单状态和 Teamly 评审页正文。
- `evaluation/main.py`：原 Excel、Word、Teamly 和邮件检查；已完整阅读并识别其关键词检查与无跨文件一致性检查的局限。
- `initial_workspace/README.md`：会议名称、日期、场地和动态服务入口。
- `groundtruth_workspace/Submissions.xlsx`、`Conference_Program.docx`：上游 Golden；已逐表、逐段读取并逐页渲染。上游 Excel 打印时严重截断，上游 Word 还加入了输入未支持的 A.P. Smirnov 生卒年与履历，因此不直接作为本题 Golden。
- Cowork-Bench 根目录 `LICENSE`，固定 commit `d943e75bc0fc8e3b27141979300cd8cbcd1e890d`。

以上可再分发快照保存在本目录。

## 动态状态如何物化

- `conference_submissions.json` 是上游 `SUBMISSIONS` 中 10 份 forms 响应的逐字段静态化；没有新增、删减或改写作者、邮箱、单位、题目、主题和摘要。
- `review_scores.md` 是上游 Teamly 评审页的 10 行、30 个评分静态化。
- `conference_rules.md` 只整理上游 Query 中已经明确的会议日期、分会场、时段、阈值和通知规则，不新增业务事实。
- 原 Teamly 写入和真实邮件发送改为 `Program_Page.md` 与 `Author_Notifications.mbox`，保证 Harbor 无网络、无外部副作用且可确定回放。

## 对上游的必要改造

- 保留全部申请、评分、阈值、日期、分会场、主题和邮件收件人，不编造新的会议记录。
- 将上游动态 SaaS 状态离线化，使 Agent 无需数据库或账号即可完整回放。
- 上游 Excel 只保存静态平均分和状态，本题改为公式化决策、公式化跨表引用和控制汇总。
- 上游 evaluator 只检查部分姓名、关键词和邮件数量；本题 Judge 将从输入独立重算全部申请、评分、决策、排期与十封通知，并检查四文件一致性和隐私隔离。
- 上游 Golden 的 Word 编造了未由输入支持的生卒年与履历，本题明确禁止此类无来源断言。

## 许可、隐私与泄漏

来源为 Apache-2.0 的 Cowork-Bench fixture，所有作者、邮箱、论文与评分均来自上游合成会议状态，因此保守标记 `synthetic=true`。本题与任何使用相同 `academic-conf-volga-rus-kazan` 申请、评分或日程的变体必须进入同一 leakage group，不能跨 Benchmark split。
