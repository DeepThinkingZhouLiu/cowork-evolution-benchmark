# 改造说明

本题逐题改造自 OmegaUse-OfficeVal 的 `officeval_068`，精确来源版本为 `ffbeecb8752447c8e40b594a0eeb1db7236ecb36`。

- `upstream-task.json`：上游真实 Query、10 页 PDF 和 18 页 PPTX 地址，原样保留。
- `upstream-rubric.json`：上游逐项评分要求，原样保留。
- `../tests/upstream_verifier.py`：上游逐题 Verifier，原样保留。
- `LICENSE-OmegaUse-OfficeVal`：上游 Apache-2.0 许可证。

本 Benchmark 没有自编 Query 或输入文件。改造时先逐页查看 PDF 的 10 页和 PPTX 的 18 页，确认真实合并关系是 `PDF 1–8 -> PPT 1–12、14、15、17 -> PDF 9–10`，最终正好 25 页。PDF 原稿是米色视觉、PPT 原稿是浅蓝/深蓝混合视觉；Golden 逐页把 PDF 的文字、卡片、流程、箭头和示意结构重建为 PowerPoint 原生对象，再保留并重排 15 张指定 PPT 页，最后统一浅蓝背景、标题层级、圆角框和连续页码。没有把 PDF 或页面渲染图贴成截图。`solve.py` 只重放这一个真实任务，不会生成别的题目。

原始 Verifier 对真实 Query 有三类可复现的误判：

- 页序规则把最终第 1 页封面硬编码为必须含“云岚”“调度坐席”等第二份 PPT 的关键词，因此真实 PDF 封面“应急有线人工通信保障网”会被判错。
- 可编辑性规则先把所有带文字的原生流程框排除，再要求每页必须存在空的流程框、箭头、圆形、图标、分隔线和示意结构；它也把 `<=14pt` 的文字全部归为说明，却同时要求每张 PDF 页必须另有 `>14pt` 正文。这些不是原始 Query 的要求，也会漏掉实际可编辑的带文字形状。
- 页码规则把位于页面左侧边缘的目录编号、章节号和流程步骤号误认成页码，因此会把同一页的 `01/02/03/04` 与右下角真实页码视为冲突。

Golden 在上游 Verifier 的浅蓝风格项得到 `5/5`，其余三项因上述误判不计分。原始 Verifier 保留在任务中供审计；本地 Judge 不放宽真实目标，而是按源文件逐页文字保持、固定 25 页顺序、PDF 十页关键语义、零栅格截图、全页浅蓝背景、右下角页码区域和 LibreOffice 实际渲染检查。
