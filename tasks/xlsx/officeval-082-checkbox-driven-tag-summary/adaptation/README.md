## 真实标准答案是怎么来的

- Query、输入标签、分类和上游 Rubric 均原样来自公开数据；本项目没有编写新的用户问题，也没有编造输入标签。
- 我先逐项核对了 126 个标签和截图目标区域，再为每个非空 B/C 单元格分别增加只属于本标签的 `□ 标签,☑ 标签` 双态下拉。它是办公软件中的真实可点击单元格控件，不是绘制出来的方框图片。
- 右侧不是复制静态答案。隐藏的 L/M 公式为 B/C 已选项生成唯一顺序，I:J 的 252 个可编辑公式按该顺序返回分类和标签。所有公式都启用打开时自动完整重算。
- Golden 预置 B5、B20、C6、C40 四个源文件中的真实标签，只用于让人打开后立刻看到跨 B/C 联动；它们分别显示新用户、市场运营、线下体验偏好和夜间使用，用户可以继续取消或更换。
- `solution/solve.py` 是围绕这一道真实工作簿写的逐题复现代码：它固定校验两个输入 SHA256、唯一工作表、行列边界和 126 个标签，不会从模板批量制造其他题目。

## CoworkEvoBench 改造决策

- 原始 Query 逐字保留，只增加输入文件名、固定输出路径、实际工作表名、可编辑性和禁止截图替代的 Harbor 交付边界。
- 采用逐单元格数据验证下拉，而不是宏或 126 个浮动表单对象。这样在 Excel、WPS 和 LibreOffice 中都可编辑，且不会遮挡原标签；选择 `□` 即取消，选择 `☑` 即勾选。
- B/C 保留为真实标签单元格；A、B、C、I、J 的列宽按上游明确区间调整，已选单元格用条件格式显示浅绿色，右侧区域使用 22 磅行高和可读字体。
- I:J 最多容纳 126 个已选项；辅助公式放在隐藏的 L/M，不在右侧泄露 TRUE、FALSE、序号或错误值。
- Judge 不要求答案采用与 Golden 完全相同的辅助列，但会要求上游控件/联动判据通过，并实际改写输入状态后重算结果。
